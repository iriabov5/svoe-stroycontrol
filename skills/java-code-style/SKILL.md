# Правила Java проекта

Перед изменением Java-кода прочитай AGENTS.md и релевантный OpenSpec change. Эти правила отражают явно подтверждённые предпочтения владельца проекта.

## Хранение и ответственность

- Прикладной доступ к БД — через JPA и репозитории своего модуля. Не использовать JdbcTemplate, JdbcClient, прямой JDBC или SQL в сервисах. Не подменять JDBC универсальной обёрткой над EntityManager.
- SQL в интеграционных тестах допустим для подготовки исторической схемы и непосредственной проверки ограничений Flyway; это не слой хранения приложения. JDBC-драйвер PostgreSQL остаётся транзитивной инфраструктурой JPA.
- CRUD выражать средствами Spring Data JPA; специализированные выборки — типизированным JPQL/HQL в конкретном репозитории. Параметры запроса связывать, не вставлять значения конкатенацией.
- Не читать таблицы и не использовать репозитории чужого бизнес-модуля. Межмодульные операции выполняются через узкий публичный интерфейс; передаются ID и модели контракта, а не JPA-сущности.
- Сервисы отвечают за права, бизнес-переходы и транзакции; репозитории — за хранение; контроллеры — за HTTP. Сохранять ограничения БД, версии, порядок блокировок и идемпотентность при рефакторинге.
- Соблюдать SOLID, KISS и DRY: не вводить общий базовый сервис, универсальный DAO, отражение или фабрику ради устранения небольшого локального сходства.

## Lombok и создание объектов

- Механические конструкторы внедрения final-зависимостей генерировать через `@RequiredArgsConstructor`.
- Не писать вручную конструктор, который присваивает параметры, генерирует UUID и ставит текущее время. UUID и время создания инициализировать в полях; обязательные входные поля и конструктор выражать средствами Lombok. Для JPA оставлять защищённый `@NoArgsConstructor`.
- Создание объекта с несколькими полями выражать через `@Builder`, а не `new` с цепочкой сеттеров. UUID, время и начальное состояние при необходимости задавать через `@Builder.Default`; JPA-конструктор оставлять защищённым. Сеттеры предназначены для изменений уже существующей сущности, а не сборки нового объекта.
- Для значимых правил создания использовать именованный метод/фабрику с документированными инвариантами. Явный конструктор допустим, если технически необходим вызов `super` или особая инициализация ресурса; объяснять причину. Не переносить механический конструктор в столь же механическую фабрику.
- Аксессоры генерировать Lombok; не применять `@Data` к JPA-сущностям и не открывать сеттеры внешним модулям. Не генерировать `equals`, `hashCode` и `toString` со связями или секретами.

## Строки и импорты

- Для многострочных постоянных запросов и шаблонов использовать текстовые блоки Java 25. Не разбивать один литерал на цепочку `"..." + "..."`. Простые короткие строки оставлять обычными литералами.
- JSON формировать сериализатором из модели, record или карты. Не экранировать и не собирать JSON конкатенацией; текстовый блок уместен для постоянной тестовой фикстуры.
- Использовать обычные импорты: `Map`, `JsonInclude`, `RequiredArgsConstructor`, `Propagation` и т. п. Полное имя типа в коде и Javadoc оставлять только при реальном конфликте имён. Не использовать wildcard-импорты.

## Форматирование и читаемость

- Использовать отступ в 4 пробела, без табуляций. По одному полю, объявлению и оператору на строку; не склеивать объявления через `;`. Аннотации классов и полей размещать на отдельных строках.
- Раскрывать тела сервисных методов, контроллеров, условий и циклов на читаемые строки. Не оставлять целый метод с проверками, изменениями состояния и return в одной строке. Разделять логические шаги пустой строкой; длинные builder-цепочки записывать по одному вызову на строку.
- Соблюдать пробелы вокруг `=`, операторов и после запятых; отделять импорты, Javadoc, объявления классов и методов пустыми строками. Для блоков условий и циклов использовать фигурные скобки, кроме очевидного короткого защитного условия по принятому стилю проекта.
- Единый форматтер — google-java-format 2.0.0 в режиме AOSP (4 пробела) с проектным разделением аннотаций полей на отдельные строки. `./gradlew javaFormat` исправляет исходники, `./gradlew javaFormatCheck javaImportCheck` проверяет формат и ненужные полные имена типов без запуска приложения.
- Форматировать новые и изменённые Java-файлы сразу в том же рабочем шаге, включая код, записанный скриптом. Не откладывать это до конца реализации и не оставлять промежуточный нечитаемый код на просмотр пользователю. Пользовательские изменения сохранять; автоформатирование не должно менять поведение.
- Перед отчётом просматривать не только пример, но и аналогичные места в main/test. `Propagation.MANDATORY`, `JsonInclude.Include.NON_NULL`, `Map` и другие типы подключать обычными импортами; полное имя допускается только при реальном конфликте импортируемых типов.

## Javadoc по-русски

- Документировать назначение классов, интерфейсов, records, сервисов, репозиториев и контроллеров, включая package-private. Описывать контракт значимых методов независимо от их видимости.
- Первая фраза объясняет назначение. Затем — конкретные правила доступа, границы транзакции, изменения состояния, повторный вызов и конкуренция, если они относятся к операции.
- Указывать содержательные `@param`, `@return`, `@throws`, условия `null`, публичные коды ошибок. Однострочное «сохраняет данные» без контракта недостаточно. Не добавлять шаблонный перечень несуществующих гарантий.
- `{@inheritDoc}` использовать, если полный актуальный контракт описан в интерфейсе. Комментарии к очевидным генерируемым аксессорам не нужны. Во внутренних методах пояснять причины нетривиального решения, а не пересказывать код.

## Завершение

- Пройти весь затронутый код и аналогичные места, а не только пример пользователя. Удалить устаревшие помощники и документацию после рефакторинга.
- Сначала закончить исправления, затем доложить объём и оставшиеся проверки. Если пользователь потребовал разрешение на запуск, спросить его после подготовки кода; до ответа не запускать сборку, тесты, Javadoc, приложение или Compose. Не объявлять непроверенный код проверенным.
