# Архитектура

Приложение состоит из React SPA и одного процесса Spring Boot. Браузер обращается к REST API через тот же origin. PostgreSQL хранит прикладные данные, Flyway управляет схемой. SeaweedFS хранит закрытые фотографии и PDF. Docker Compose задаёт локальный контур.

Платформа зафиксирована 13 ноября 2026 года: Java 25 LTS, Gradle 9.9.1, Spring Boot 4.1.2, PostgreSQL 18.7, Node.js 26.13.1 LTS, React 19.3.1, TypeScript 7.0.2, Vite 8.3.8. Security, Data JPA, Flyway и JUnit Jupiter 6 берутся из BOM Spring Boot. Полная таблица и правило выбора версий — в [документе о версиях стека](versions.md).

Стрелка зависимости направлена от потребителя к публичному интерфейсу поставщика. Например, `acceptance` проверяет статус работ через публичный интерфейс `stages` и хранит собственный статус приёмки. Внутренние JPA-сущности и репозитории остаются внутри своего модуля. Межмодульные внешние ключи поддерживают целостность по UUID.

Файловый адаптер отвечает за запись и чтение объектов. Право на выдачу файла определяет модуль-владелец по метаданным и участию пользователя в карточке. Повтор загрузки проверяется по ключу и хешу; очистка исключает удержанные журналом или банковским пакетом объекты.

«СВОЁ Село» и «СВОЁ Жильё» смогут подключаться через интеграционные адаптеры с сопоставлением внешних идентификаторов и UUID проекта. Конкретные протоколы и поля появятся после определения внешних контрактов. Для сельской ипотеки порт `BankGateway` связывает домен с локальным Mock API. API использует отдельный маршрут с явной маркировкой демо, фиксированные сценарии и синтетические данные. Демо-действия обновляют состояние симуляции.

Границы первой поставки и детали сессии, транзакций и миграции описаны в [документе о версиях стека](versions.md).

## Этапы строительства

`stages` владеет таблицей `construction_stages`, правилами переходов и расчётом задержек. Участие в карточке проверяется через `Projects`; сущности и репозитории `projects` наружу не передаются. Все записи этапов блокируют карточку через публичный интерфейс внутри текущей транзакции, чтобы добавление, перестановка и проверка участников были согласованы. `@Version` и версия в командах защищают от устаревшего сохранения. Уникальность позиции проверяется на commit, что позволяет обменять позиции в одной транзакции.

Плановые и фактические значения — календарные даты. Источник текущей даты — внедряемый Clock в Europe/Moscow. Просрочки вычисляются при чтении. Статус завершения работ принадлежит `stages`; принятие работ принадлежит `acceptance`.

## Подготовка и согласование

Новая карточка проходит заявку, предложение и договор. Назначенный подрядчик получает доступ после отправки заявки. Отправленные версии неизменяемы; заказчик видит только отправленные пакеты. Согласование сметы создаёт запланированные этапы, согласование договора открывает начало работ. История решений сметы и договора разделена. Согласование в приложении не является электронной подписью.

`proposals` использует публичные Projects и Stages: одна блокировка карточки координирует версии и решения, одна транзакция сохраняет решение, ссылку исходного пакета и весь план. Все прикладные данные сохраняются через JPA-сущности и репозитории своего модуля. Типизированные JPQL/HQL-запросы находятся в специализированных репозиториях; JDBC в бизнес-коде не используется. Сущности и репозитории за границы модулей не передаются.

V3/V4 сохраняют уже существовавшие карточки как LEGACY; их план не требует фиктивного согласования задним числом. Новые карточки всегда PROPOSAL_REQUIRED. Исходная цена и план доступны обеим сторонам, кредитные сведения — только владельцу. Ипотечный Mock API слушает loopback внутри backend, импорт выполняется вне транзакции с повторной проверкой версии заявки перед записью. Снимки и результаты повторов принадлежат banking.

Иллюстрации предложения — HTTPS URL и подписи; сервер не скачивает их оригиналы. Модуль files принимает бинарные вложения для журнала и банковских подтверждений, сохраняя закрытые объекты в SeaweedFS.

Lombok для внедрения зависимостей и Builder для создания многополевых сущностей.

## Организация и авторство

accounts владеет личным именем и версией профиля; organizations — реквизитами, членством, приглашениями и сохранёнными ключами приглашений. projects хранит назначенную организацию и явные DOCUMENTS/WORKS назначения конкретной стройки. Проверка актуальных прав сериализуется с отзывом через блокировку организации, затем проекта. Сессионный профиль не является источником разрешений.

proposals и journal сохраняют ActorSnapshot в собственных таблицах. Связи между модулями — публичные интерфейсы Accounts/Organizations/Projects, идентификаторы и модели без чужих JPA-сущностей. Для прежних записей нет выдуманных персональных данных.

## Закрытые вложения

files владеет attachments и S3-адаптером (AWS SDK v2), journal хранит только ID вложений. Загрузка состоит из короткой транзакции намерения, внешнего S3-вызова и повторной проверки прав перед READY. Публикация удерживает все вложения одной транзакцией с записью журнала. Очистка помечает временный объект DELETING под той же блокировкой, поэтому не удаляет опубликованные подтверждения. Бакет SeaweedFS закрыт, выдача проходит через сессионный API с no-store/nosniff. Документы BANK доступны только владельцу ипотечного проекта.

## Приёмка, демо-банк и завершение

acceptance владеет циклами сдачи, снимками подтверждений из публичного Journal, решениями и результатами идемпотентных команд. Сначала блокируются актуальная организация и проект через Projects, затем проверяются права, версия этапа и допустимое состояние. Частичные уникальные индексы запрещают две открытые или две принятые сдачи одного этапа. Даты выполнения остаются в stages.

banking сохраняет неизменяемый пакет, версии дополнений и попытки доставки. HTTP выполняется вне транзакции; короткая аренда с токеном исключает параллельную обработку. При неизвестном исходе тот же ключ сначала запрашивается у Mock API, а не создаёт новое подтверждение. Получение отделено от окончательного решения; автоматические повторы ограничены тремя попытками, доступен явный повтор владельцем. Mock API хранит квитанции в БД и слушает только loopback backend.

Кредитный снимок исходной заявки не переписывается при позднем подключении синтетического дела. Только владелец читает полный банковский пакет; публичный BankStageStatus отдаёт подрядчику статус без кредитных данных. Замкнутый цикл зависимостей исключён отдельным сервисом чтения статусов.

projects владеет итогом строительства. CompletionService читает публичный Acceptance под блокировкой проекта, проверяет непустой полностью принятый план и сохраняет дату/автора. Банковский статус не является условием завершения. Закрытый проект запрещает новые работы и обсуждения; история и банковские дополнения остаются доступны по прежним правам.

## Изображения сметы

Файловый модуль хранит PROPOSAL-вложения, proposals — ссылки на них, порядок и подписи конкретной версии. Узкая граница ProposalFiles проверяет наличие черновика и видимость файла; реализация читает только репозитории proposals и не зависит от файлового сервиса. Это исключает циклическое внедрение. Изображение черновика не выдаётся заказчику по прямому URL. Предпросмотр использует защищённый файловый API; локальная миниатюра до сохранения — object URL браузера, не подтверждение загрузки.

## Проверка участка и предварительная ипотека

`projects` владеет сохранённым кадастровым номером и состоянием строительной заявки. Публичный `FinancingRequests` отдаёт владельцу неизменяемый контекст с номером, версией и доступностью записи; вариант с блокировкой требует активной транзакции и соблюдает общий порядок «организация → проект». Чужие JPA-сущности и репозитории в banking не передаются.

`banking` владеет таблицами V12: `project_financing_plans`, `project_plot_checks`, `project_mortgage_calculations`, `financing_planning_commands`. Результаты неизменяемы, план хранит указатели и версию, успешная команда — нормализованный отпечаток и точный ответ для безопасного повтора. Составные внешние ключи исключают ссылку на проверку или расчёт другой карточки. Модуль не меняет пожелания, источник финансирования, согласованную смету и снимки одобрения при сохранении расчёта.

Проверка участка расширяет существующий loopback Mock API маршрутом `/plot-check`. HTTP выполняется без транзакции; после ответа повторно проверяются права, состояние, номер и версии под блокировкой проекта. Результат, указатель и ответ команды фиксируются атомарно. После сетевого сбоя успешный ключ не записывается, предыдущие результаты остаются. Серверный аннуитет использует DECIMAL128 и финальное HALF_UP до копеек; браузерный предварительный просмотр не является сохранением.

Текущий `frontend/` использует общий сессионный клиент, сгенерированные API-типы и токены оформления. Состояние очищается при смене карточки и выходе; отменённый ответ прежней карточки не обновляет новую. Детальные результаты доступны исключительно владельцу через отдельный ресурс с no-store, в общую карточку/заявку подрядчика не включаются. Статусы актуальности определяются текущим номером и основанием расчёта, а не давностью просмотра. Новые runtime-зависимости не добавлены.

### Навигатор строительства

Guidance читает авторизованные контексты, планы, последние циклы приёмки и подтверждения наборами в read-only REPEATABLE_READ-транзакции. Сводка и карточка используют один чистый расчёт; frontend использует canAct и primaryPointId, не повторяет правила по общей роли. Передача дома и существующее завершение используют общее правило готовности приёмки. Модуль stages не зависит от journal/acceptance, поэтому новая агрегация не создаёт цикла внедрения. Байты S3 и банковские API при чтении не вызываются.

Projects владеет таблицей project_construction_profiles (материал стен, фундамент и кровля). Площадь/этажность и срок не дублируются: это проекция заявки и полного действующего плана. Состояния контрольных точек и счётчик не сохраняются. Фотография считается опубликованным подтверждением только как READY-изображение JOURNAL, удерживаемое NOTE нужных проекта и этапа. Внешняя ссылка или PDF не заменяют его.
