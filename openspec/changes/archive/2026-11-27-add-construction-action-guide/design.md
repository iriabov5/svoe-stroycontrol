# Контрольные точки, действия и паспорт дома

## Context

Цель и объём — в [proposal](proposal.md). Предложенная первая итерация согласована запросом пользователя «реализуй» 27 ноября 2026. Дополнительное уточнение подтвердило компактный UI и инструкцию docs/control-gates-demo.md в объёме.

Проверенная база: `main` 82375dc, один Spring Boot backend и существующий React frontend. В stages есть вид, порядок и состояния PLANNED/IN_PROGRESS/WORK_COMPLETED. В acceptance есть циклы OPEN/RETURNED/ACCEPTED; решение не меняет WORK_COMPLETED обратно. В projects есть подтверждённое завершение, права команды и строительная заявка с areaM2/floors/desiredFinish. Journal хранит attachmentIds отдельно от внешних photos; закрытые вложения предоставляет files. V12 уже занята проектным планированием ипотеки.

Ветка `codex/control-gates-demo` — только функциональный референс, её коммиты, V12/V13, демо-обход процесса и готовые обработчики не переносятся. Проектные инструкции, стек и текущая ипотечная функциональность сохраняются.

## Goals / Non-Goals

**Goals:** один серверный расчёт для карточки, выделения этапов и сводки; read-only проекции из актуальных источников; изоляция данных и действующие полномочия; проверяемые переходы полного цикла; воспроизводимая документация.

**Non-Goals:** новый workflow приёмки, сохранённая очередь уведомлений, фоновые jobs, отдельный сервис, ИИ, определение качества работ, автоматическое подтверждение этапов или изменение уже отправленной заявки. Смежные proposals бюджета/помощника не реализуются.

## Decisions

### D1. Статус и отличия от референса

| Решение | Статус | Основание |
|---|---|---|
| Самостоятельная реализация в текущем приложении | Запрошено пользователем | Доработка существующего проекта |
| Полный цикл точек из нормативной таблицы specs | Согласовано запросом на реализацию | Закрывает ошибки возврата, повторной сдачи и завершения |
| Точки всех этапов FOUNDATION/UTILITIES в трёх группах | Согласовано запросом на реализацию | Нельзя терять второй фундамент или вторую очередь сетей |
| Только закрытые опубликованные фото как подтверждения | Согласовано запросом на реализацию | Совпадает с используемыми при сдаче реальными вложениями; внешняя ссылка остаётся иллюстрацией |
| Сводка объектов с действиями на backend | Согласовано запросом на реализацию | Нельзя повторять правила и упрощать права команды до общей роли |
| Паспорт как проекция плюс три дополнительных характеристики | Согласовано запросом на реализацию | Сохраняет полезный контекст без второй копии площади, этажности и срока |
| Нет пользовательского редактора технических характеристик | Согласовано запросом на реализацию | Не расширять задачу новым процессом записи и согласования |

Это конкретный проект для согласования; существенных неразрешённых развилок внутри предложенного варианта нет. Принятие proposal должно включать решения D1, иначе артефакты пересматриваются до кода.

### D2. Владельцы данных и направление зависимостей

| Модуль | Принадлежащие данные | Узкий интерфейс чтения для guidance |
|---|---|---|
| projects | Карточка, доступ, команда, заявка, завершение, дополнительные характеристики | Авторизованный контекст: ID/название, права, режим/закрытие подготовки, факт договора/завершения; безопасные поля паспорта |
| stages | Исполняемый план и фактические состояния | План доступной карточки, без JPA-сущностей |
| acceptance | История циклов и решение | Последний цикл по каждому stageId, принятые этапы и наличие открытых циклов; не чтение внутренних repositories |
| journal | Публикации и связь с вложениями | Наличие подходящей опубликованной NOTE по stageId, без текста и персональных данных |
| files | Метаданные/готовность/тип/принадлежность файлов | Готовые метаданные через существующий Files.describe или специализированное чтение в своей границе |
| guidance, новый модуль | Правила подсказок, REST-модели точек и сводки; собственных таблиц нет | Сборка read-only ответов из перечисленных контрактов |

Новый модуль оправдан конкретной границей: агрегирование stages + acceptance + journal + projects в одном направлении. Не помещать зависимости на acceptance/journal внутрь stages, поскольку эти модули уже используют stages. Для guidance не нужны собственный repository, общий DAO, очередь или общий базовый сервис. Коллаборации — публичные интерфейсы с ID и моделями значений; один Spring Boot runtime.

Получать последние циклы и подтверждения наборами по уже авторизованным ID этапов. Не делать по запросу на каждый этап и по HTTP-запросу на каждый объект из frontend. Новые индексы вводить только после проверки существующих индексов и плана реальной выборки; не добавлять индексы «на всякий случай».

### D3. Вычисление и согласованность

Нормативная таблица переходов — [specs/construction-control-gates](specs/construction-control-gates/spec.md), requirement «Состояния точки соответствуют полному циклу этапа». У каждого этапа используется последний cycleNumber, не произвольная ранее принятая или возвращённая сдача. HANDOVER переиспользует то же правило готовности, что существующая сводка завершения: непустой полностью принятый план без OPEN-циклов. Правило хранится у владельца готовности и предоставляется публичным чтением, а не копируется в guidance.

Признак фото строится на NOTE данного проекта/этапа со статусом PUBLISHED и готовым удерживаемым изображением из attachmentIds. Не использовать одну таблицу JournalPhoto, не вызывать удерживающие/изменяющие методы при GET и не получать байты из S3 для каждого расчёта. Тип проверяется по сохранённым доверенным метаданным files. Просмотр изображения продолжает проверять сессию и доступ отдельным запросом к существующему защищённому URL.

Каждое чтение выполняется в одной read-only транзакции PostgreSQL со стабильным снимком (предлагается REPEATABLE_READ). Внешних банковских вызовов и S3 GET в расчёте нет. Сам запрос не блокирует рабочий процесс и не создаёт записей. Авторизация и набор источников читаются в рамках этого снимка. После зафиксированной смены доступа следующий новый запрос проверяет актуальные права. Общего межпользовательского кеша нет.

Повтор GET не требует idempotencyKey. Обновление статуса происходит через уже существующие команды с CSRF, версиями, блокировками и идемпотентностью; никакой отдельной POST «пройти точку» не добавляется. В точках нет версий для записи. Два параллельных одинаковых GET читают данные, но ничего не создают. Невозможная комбинация источников даёт GUIDANCE_READ_FAILED по текущему Problem-контракту, с безопасной диагностикой, а не ложный COMPLETED.

### D4. Предлагаемый REST-контракт

Все пути ниже относительно `/api/v1`. Новые операции только GET. Path projectId — обязательный UUID по существующему ProjectId; действующая сессия обязательна. Query-параметры не требуются, фильтра по роли/пользователю/произвольным ID нет. Сначала внести операции и типы в `api/openapi.yaml`, затем сгенерировать frontend-типы. Сейчас контракт не изменяется.

| Метод и путь | Доступ и назначение | 200 |
|---|---|---|
| GET `/projects/{projectId}/control-gates` | Текущий участник карточки; точки и персональный следующий шаг | ControlGatesView |
| GET `/construction-actions` | Вошедший аккаунт; все доступные ему объекты с canAct, без клиентского N+1 | ConstructionActionsView |
| GET `/projects/{projectId}/construction-profile` | Текущий участник карточки; безопасный паспорт | ConstructionProfile |

**ControlGatesView:** обязательные projectId(UUID), computedAt(date-time UTC), completedAt(date-time UTC|null), groups(array ровно из трёх групп), primaryPointId(string|null), actionablePointCount(integer >=0).

**Группа:** обязательные key(enum FOUNDATION/UTILITIES/HANDOVER), title(string), points(array). Отсутствие вида работ — points:[], frontend показывает пояснение. HANDOVER содержит одну точку даже при пустом плане; primaryPointId всегда указывает на возвращённую точку либо null. Персональный выбор primary — на сервере по нормативному приоритету, не второй алгоритм в React.

**Точка:** все перечисленные поля обязательны; неизвестное/неприменимое передаётся null, не отсутствующим полем:

| Поле | Тип / смысл |
|---|---|
| id | Стабильная строка `FOUNDATION:<stageId>` / `UTILITIES:<stageId>` / `HANDOVER:<projectId>` |
| stageId | UUID|null; null только у передачи дома |
| title | Пользовательский заголовок с названием этапа при нескольких точках |
| status | BLOCKED / WAITING_CONTRACTOR / WAITING_CUSTOMER / COMPLETED |
| reasonCode | PREPARATION / PREPARATION_CLOSED / CONTRACT_REQUIRED / START_REQUIRED / EVIDENCE_REQUIRED / EVIDENCE_PUBLISHED / SUBMISSION_REQUIRED / ACCEPTANCE_OPEN / CORRECTIONS_REQUIRED / STAGE_ACCEPTED / ACCEPTANCE_REQUIRED / COMPLETION_REQUIRED / PROJECT_COMPLETED |
| detail | Текст причины, не техническое имя статуса и не кредитные сведения |
| responsibleRole | CUSTOMER / CONTRACTOR / null для завершённого или неприменимого действия |
| canAct | boolean: разрешён ли текущему аккаунту указанный следующий шаг |
| action | `{code,label}` или null; код OPEN_START / OPEN_JOURNAL / OPEN_SUBMISSION / OPEN_ACCEPTANCE / OPEN_CORRECTIONS / OPEN_COMPLETION |
| target | Навигация чтения: `{projectId,stageId,section,submissionId}` либо null; section PROJECT / WORK / JOURNAL / ACCEPTANCE / COMPLETION |
| acceptedStageCount / totalStageCount | integer >=0 либо null; заполнены только у HANDOVER |

`action` возвращается только при WAITING-состоянии и canAct=true; canAct=false означает action:null, но target может вести к разрешённому чтению. Нельзя вернуть готовый произвольный URL или обещание разрешить команду: frontend строит маршрут из проверенных идентификаторов, а команда заново проверяет backend-права. Для BLOCKED/COMPLETED canAct=false. Например, stageId у ACCEPTANCE_OPEN — этап, submissionId в target — последний OPEN-цикл.

**ConstructionActionsView:** обязательные computedAt(date-time), projectCount(integer >=0), projects(array). Один элемент `{projectId,projectName,primaryPointId,target}` на объект с хотя бы одной точкой canAct=true; primaryPointId — главная доступная точка этого объекта. projectCount равен projects.length, порядок — название в нижнем регистре после trim и затем UUID. Пустая успешная сводка: projectCount:0, projects:[]. Карточки без доступа не включаются, идентификаторы и имена недоступных карточек не раскрываются. При ошибке чтения источника всей сводки возвращается Problem, а не «успех без части объектов». Загрузка сведений выполняется наборами в backend; не вводить неподтверждённый лимит/пагинацию, который скрывает часть счётчика.

**ConstructionProfile:** обязательные projectId, areaM2(number|null, текущие ограничения заявки), floors(integer|null, ограничения заявки), wallMaterial/foundationType/roofType(string|null, до 120 символов), plannedFinish(date|null), desiredFinish(date|null), sources(object). sources содержит одноимённые ключи значений с enum REQUEST_DRAFT / REQUEST_SUBMITTED / AGREED_PLAN / LEGACY_PLAN / PROFILE или null. Для отсутствующего значения источник null. Пожелание desiredFinish не выдаётся за plannedFinish. Площадь хранит точность существующего числового значения; units отображаются в UI.

**Ошибки:** переиспользовать актуальную форму Problem (type/title/status/code/fieldErrors) и общие ответы из OpenAPI. Связь с безопасным журналом остаётся через существующий requestId; нового поля traceId в ответе не предполагать. 401 AUTH_REQUIRED — нет сессии; 400 VALIDATION_ERROR — некорректный UUID/параметры по действующим общим правилам; 404 PROJECT_NOT_FOUND — отсутствующий или чужой проект; 500 GUIDANCE_READ_FAILED — **предлагаемый новый код**, ошибка чтения или противоречивые данные. В текущем ApiError такого кода нет: добавить и описать его вместе с ответом 500 до реализации новых GET. Обработка ограничена guidance, не меняет существующие ошибки других модулей; внутренняя причина остаётся только в безопасной диагностике. Инфраструктурный 503 frontend также обрабатывает как недоступность. Ошибок 409 при GET не вводить. Заголовки кеширования сохраняют текущую политику закрытых данных; request использует no-store. CSRF для существующих команд не ослабляется.

### D5. Паспорт и изменения PostgreSQL

Паспорт собирает guidance: безопасные данные заявки/дополнительных характеристик читает у projects, план — у stages. Не заставлять projects зависеть от guidance. До отправки заявки черновик доступен только владельцу; у подрядчика без доступа к карточке 404, а доступный подрядчику новый проект уже использует отправленную заявку. Технический паспорт не меняет пожелания или исторические версии сметы.

Плановый срок — max(plannedFinish) **только при непустом действующем плане и заполненных датах окончания всех этапов**. Для нового процесса это исполняемый план согласованного предложения; для LEGACY — его действующий план. Если хотя бы одна дата отсутствует, plannedFinish:null. Желаемый срок заявки остаётся отдельным desiredFinish с отдельной подписью; не смешивать их молча. Материал стен не угадывается из общего materials или technology: это более широкие свободные пожелания, а не подтверждённая характеристика стен.

Предлагается одна таблица `project_construction_profiles`, владелец projects:

| Колонка | PostgreSQL | Ограничения / назначение |
|---|---|---|
| project_id | uuid | PK, FK → house_projects.id; одна запись на объект |
| wall_material | varchar(120) NULL | Материал стен, непустая после trim строка либо null |
| foundation_type | varchar(120) NULL | Тип фундамента, непустая строка либо null |
| roof_type | varchar(120) NULL | Тип кровли, непустая строка либо null |

Хотя бы одна характеристика записи должна быть заполнена; остальные могут отсутствовать. Новые записи не создаются при GET. Источники areaM2/floors — construction_requests, срок — текущий план/заявка; этих колонок в новой таблице нет. У старых проектов отсутствие строки нормально. Строки характеристик не подменяют фактическое обследование дома. Дополнительные индексы не нужны для чтения по PK. Удаление проекта подчиняется текущей политике удаления: FK не должен оставлять сирот, новый публичный delete не вводится.

В первой итерации эти три характеристики записывает только явно запущенная команда разработки в **свои созданные синтетические карточки** через операцию модуля projects. Эта запись атомарна и проверяет принадлежность seed-набору. Пользовательского mutation API пока нет, поэтому не добавляются его произвольные версии/лимиты/конкурентные обновления. Будущий редактор требует отдельного change. Альтернатива — шесть новых колонок в house_projects — отвергнута: дублирует площадь/этажность/срок и создаёт рассинхронизацию.

### D6. Frontend и обновление данных

В текущей карточке — адаптивная общая сетка обзора объекта, паспорта и подрядчика (три колонки на широком экране, одна на телефоне), компактный паспорт, главная контрольная точка с одной основной кнопкой, три группы остальных точек. Не добавлять вкладку отдельного приложения. Список этапов использует полученные точки по stageId, не делает новый собственный расчёт. Шапка получает construction-actions; правильная подпись числа объектов, не числа действий.

Для данных достаточно общего механизма загрузки/инвалидации существующего frontend; новая библиотека состояния не нужна. После успешной команды, влияющей на источник, инвалидировать соответствующие контрольные точки, паспорт при необходимости и глобальную сводку. При переходе в список, карточку, этап и при visibilitychange обратно в visible обновлять данные заново. Во время записи подсказка не опережает сохранение; после успеха виден пересчёт, после ошибки существующий введённый текст и данные формы сохраняются.

Связывать ответы с accountId/projectId и поколением запроса; поздний ответ игнорировать, при выходе очищать данные. Отдельно показывать initial loading, отсутствие точек вида/действий, обновление и ошибку с повтором. Последнее известное состояние при ошибке можно оставить с явной пометкой «Не обновлено»; оно не должно выглядеть текущим успешным нулём. Не предлагать выполнение до получения актуального ответа после мутации.

Маршруты к уже существующим секциям строит общий helper, не сервер. При необходимости расширить текущий hash-router поддержкой безопасного query `section=journal|acceptance|completion` и ID выбранного цикла; query не становится частью stageId. После загрузки целевой секции прокрутить её в видимость и переместить фокус на заголовок. Маршрут HANDOVER — карточка проекта, section=completion. Начало/сдача/приёмка остаются отдельными явными действиями пользователя, ссылка ничего не записывает.

### D7. Демонстрация, снимки и критерии проверки

Команда разработки создаёт изолированные новые аккаунты/организацию/команду и проекты, проходит штатные REST-команды подготовки, согласования и выполнения. Прямой SQL смены process_mode, внедрение contractor_id и подмена приёмки запрещены. Dev-runner для дополнительных характеристик работает только в явно выбранном локальном профиле/команде и только на своих seed-ID; это не открытый production endpoint. Набор и его маркер выводятся вместе с синтетическими реквизитами. Повторный запуск не меняет чужие или старые данные; частичный сбой завершается с понятным шагом и безопасным повтором по собственному маркеру/ключам.

Фото — синтетические изображения с заметной подписью, загруженные как READY-вложения в закрытый SeaweedFS через существующий API. Они демонстрируют сценарий, не доказывают качество. Для двух ролей нужны разные проекты/состояния; для демонстрации возврата и полного завершения — отдельные изолированные карточки, чтобы не менять снимки уже отправленной заявки. Пароли и аккаунты синтетические, секреты окружения не попадают в репозиторий.

## Risks / Trade-offs

- Фото выглядит как разрешение скрыть работы → явно разделять подтверждение публикации и приёмку, не показывать заключение о качестве и не блокировать команды точками.
- Упрощённая роль раскрывает команду сотруднику без полномочий → canAct на backend из текущих проектных полномочий; повторная проверка при самой записи.
- Два независимых источника создают устаревший счётчик → один серверный расчёт, явная инвалидация и защита от поздних ответов.
- Все проекты в сводке дают большой объём → пакетное чтение без N+1; при подтверждённом объёме отдельно согласовать пагинацию, не скрывать часть счётчика молча.
- Требуется дополнительный модуль → он оправдан только агрегацией уже существующих владельцев и не получает универсальный слой хранения.
- Характеристики пока редактируются лишь в dev-сценарии → явно показывать отсутствие значений обычных домов; будущий редактор отдельно, без демонстрационных подстановок.

## Migration Plan

1. Согласовать первую итерацию proposal/specs/design; до этого код и OpenAPI не менять.
2. Перед реализацией сверить main и docs/versions.md с BOM/lock/образами. Сначала расширить OpenAPI и проверить контракт, затем реализовать по tasks.
3. Следующая миграция после текущей V12 — ориентировочно V13__project_construction_profiles.sql; перед созданием проверить фактическую последнюю версию. V12 ипотеки и исторические checksum сохраняются. Миграция добавляет пустую таблицу без синтетического backfill рабочих проектов.
4. Проверить обновление копии базы, где V12 уже применена и есть проверки/расчёты/заявки/файлы. Обычные проекты продолжают работать без строки профиля. Синтетические данные создаются только явной dev-командой после запуска.
5. Откат приложения оставляет дополнительную таблицу неиспользуемой; не выполнять down-миграции и не удалять файлы или старые данные.
6. После реализации пройти проверки, обновить снимки и документацию, сверить дельты и действующие требования; только после этого синхронизировать и архивировать change через OpenSpec.
