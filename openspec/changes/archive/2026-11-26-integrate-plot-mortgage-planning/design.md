# Участок и ипотека в существующей подготовке строительства

## Context

Мотивация, статус и границы — в [proposal](proposal.md). Первая итерация согласована командой «реализуй»; документ отражает реализованную интеграцию демонстрационного контура.

Сейчас `frontend/src/Preparation.tsx` содержит форму строительной заявки с `cadastralNumber`, `desiredBudget`, `financingSource` и отдельный `MortgagePanel`. Кадастровый номер необязателен, ограничен 50 символами и при сохранении должен содержать четыре числовые группы через двоеточие; длины групп существующий валидатор не ограничивает. Поэтому, например, `1:2:3:4` можно сохранить по прежним правилам, но он не подходит для новой проверки. Адрес находится в карточке/заявке. `projects` владеет `construction_requests`, `banking` — `mortgage_approval_snapshots` и результатами импорта. Импорт использует локальный HTTP Mock API на loopback, права владельца и версию заявки. Новое планирование не меняет этот контракт.

PR изучен на head `9d7a1daf1016f9f0bb030959434b908be27f2d55`: `Home.tsx` реализует проверку трёх примеров таймером, показывает сведения и открывает калькулятор для подходящего участка; `domain.ts` содержит примеры и формулу аннуитета. В PR история проверок общая для браузерного профиля, параметры калькулятора хранятся в состоянии компонента. Серверное сохранение расчёта — предлагаемое развитие при интеграции.

## Goals / Non-Goals

**Goals:** единый путь «Мои объекты → карточка → подготовка → участок → расчёт»; текущая сессия; серверный источник результата; повторный вход и несколько карточек без смешивания данных.

**Non-Goals:** второй frontend, iframe, новый способ входа, миграция браузерных профилей PR, обращение в настоящий банк/Росреестр, юридическая проверка земли. Демо-цифры не проверяются как реальные условия программ. Демозаявки и лист ожидания не включены в предлагаемую первую поставку.

## Decisions

### 1. Размещение и интерфейс

Предлагается отдельная секция внутри `Preparation` под сведениями об участке, доступная владельцу даже при выборе собственных средств. Рядом остаётся текущий выбор финансирования и отдельный блок импорта одобрения. Весь маршрут открывается штатным `frontend/`; используются текущие hash-маршруты, API-клиент, `Field`, `Notice` и токены `shell.css`. Переносится смысл и композиция элементов PR, а не его оболочка, собственная маршрутизация и бренд отдельного продукта. Новые библиотеки не нужны.

Если форма заявки изменена, проверка предлагает сохранить черновик штатным `PATCH /projects/{projectId}/request`. После успеха используется возвращённая версия. Кнопки демопримеров заполняют существующее поле номера, явно предупреждая, что это тестовый пример; пользователь отдельно сохраняет изменение. Они не подменяют адрес карточки. При отправленной заявке поле и примеры не редактируются.

Проверка показывает загрузку, отсутствие результата, сведения/причину, неизвестный номер и техническую ошибку. Калькулятор имеет ползунки и подписанные числовые значения, предупреждение лимита, кнопку «Сохранить расчёт», отметки «Предварительный просмотр · не сохранён» и «Сохранено …». Изменение параметров в браузере не считается записью на сервер. При ответе из старой карточки UI игнорирует результат; состояние очищается при смене projectId и выходе. Несохранённые поля сохраняются в памяти текущей формы при исправлении ошибок, но не переходят другому аккаунту.

После отправки заявки, окончательного закрытия подготовки либо завершения строительства показываются сохранённые результаты, новые команды запрещены. Для `LEGACY` без черновика показывается объяснение недоступности планирования; фиктивная заявка не создаётся. Проверка не становится обязательным условием строительного процесса.

### 2. Владельцы данных и границы

| Данные | Владелец | Публичная граница |
|---|---|---|
| Карточка, владелец, адрес, состояние стройки | `projects` | `Projects`, модели без JPA-сущностей |
| Кадастровый номер, версия и состояние заявки | `projects` | Узкая модель чтения/проверки версии планирования; расширить публичный интерфейс заявки |
| Результаты проверки, условия и расчёты | `banking` | Новые сессионные операции планирования |
| Существующее одобрение и его импорт | `banking` | Существующие `/mortgage-approval` и `/mortgage-approval/import` |

Новый бизнес-модуль не предлагается: здесь проверяется только пригодность тестового участка к демонстрационной ипотеке, что относится к `banking`. Доступ к чужим таблицам и репозиториям запрещён. Узкая граница заявки возвращает projectId, ownerId, cadastralNumber, requestVersion и возможность редактирования после проверки владельца; для записи проверяет их под общей блокировкой проекта. Имена интерфейса уточняются при реализации без изменения поведения. Кредитный расчёт не добавляется в общедоступную модель заявки и не раскрывается подрядчику.

### 3. Модель хранения

Все перечисленные таблицы — новые, принадлежат `banking`, записи выполняются через JPA. Номер миграции выбирается следующим свободным при реализации: другие планируемые changes также претендуют на V12. Применённые миграции не редактируются.

| Таблица | Поля и ограничения |
|---|---|
| `project_financing_plans` | `project_id uuid PK/FK house_projects`, `version bigint NOT NULL >=0`, `latest_plot_check_id uuid NULL`, `latest_calculation_id uuid NULL`; отсутствие строки в API означает version=0 |
| `project_plot_checks` | `id uuid PK`, `project_id uuid NOT NULL FK`, `owner_id uuid NOT NULL FK accounts`, `cadastral_number varchar(50) NOT NULL`, `request_version bigint NOT NULL >=0`, `status varchar(20) NOT NULL IN (ELIGIBLE, INELIGIBLE, NOT_FOUND)`, `address varchar(300) NULL`, `region varchar(200) NULL`, `land_category varchar(200) NULL`, `permitted_use varchar(200) NULL`, `reason varchar(1000) NULL`, `terms_version varchar(50) NULL`, `rate numeric(6,3) NULL`, `checked_at timestamptz NOT NULL`, `is_demo boolean NOT NULL CHECK(is_demo)` |
| `project_mortgage_calculations` | `id uuid PK`, `project_id uuid NOT NULL FK`, `owner_id uuid NOT NULL FK`, `plot_check_id uuid NOT NULL FK`, `cost numeric(15,2)`, `deposit_percent integer`, `deposit_amount numeric(15,2)`, `years integer`, `joint boolean`, `principal numeric(15,2)`, `rate numeric(6,3)`, `credit_limit numeric(15,2)`, `monthly_payment numeric(15,2)`, `within_limit boolean`, `terms_version varchar(50)`, `calculated_at timestamptz`, `is_demo boolean CHECK(is_demo)`; все параметры и результаты NOT NULL |
| `financing_planning_commands` | `id uuid PK`, `project_id uuid NOT NULL FK`, `owner_id uuid NOT NULL FK`, `idempotency_key uuid NOT NULL`, `operation varchar(20) NOT NULL IN (CHECK,CALCULATE)`, `request_hash varchar(64) NOT NULL`, `result jsonb NOT NULL`; UNIQUE(project_id, owner_id, idempotency_key) |

Добавить CHECK диапазонов калькулятора из specs. Для ELIGIBLE обязательны сведения об участке, rate и termsVersion, reason=null; для INELIGIBLE сведения и причина обязательны, rate/termsVersion=null; для NOT_FOUND все сведения и rate/termsVersion=null, причина «Участок отсутствует в демобазе». Для nullable rate задать неотрицательность. Версия условий идентифицирует неизменяемый набор демонстрационных правил, например `pr1-demo-v1`.

Составные уникальные ключи `(project_id,id)` и соответствующие FK для ссылок плана и расчёта гарантируют принадлежность результатов той же карточке; связь расчёта с подходящей проверкой и её owner проверяет сервис в транзакции. Индексы последних результатов покрываются PK/UNIQUE; отдельные индексы без запроса не добавляются. Технический сбой не становится INELIGIBLE и не создаёт успешный результат команды.

Результаты неизменяемы, план содержит указатели на последние. Историю списком в первой итерации не выводить: это не глобальная история PR. Существующие карточки не заполняются выдуманными результатами; строки появляются при первой успешной записи. Браузерные данные PR не импортируются. При копировании заявки другому подрядчику результаты не копируются в новую карточку. Данные сохраняются как история проекта, фоновая очистка в этом change не вводится.

### 4. Предлагаемый REST-контракт

Пути ниже относительны `/api/v1`. Все операции используют существующую cookie-сессию, проверяют владельца и возвращают `Cache-Control: no-store`. Новые POST защищены общим CSRF. Неизвестные поля запрещены. До реализации добавить схемы и примеры в `api/openapi.yaml`, проверить lint и сгенерировать `frontend/src/api/schema.d.ts`.

| Метод и путь | Назначение и тело | Успех |
|---|---|---|
| GET `/projects/{projectId}/financing-planning` | projectId — обязательный UUID; тела и query нет | 200 `PlanningView` |
| POST `/projects/{projectId}/financing-planning/plot-checks` | обязательные `requestVersion: integer >=0`, `planningVersion: integer >=0`, `idempotencyKey: UUID`; номер сервер читает из сохранённой заявки | 200 `PlanningView` после проверки и сохранения |
| POST `/projects/{projectId}/financing-planning/calculations` | те же три поля плюс `plotCheckId: UUID`, `cost: number`, `depositPercent: integer`, `years: integer`, `joint: boolean`; все обязательны, null не допускается; диапазоны и шаги из specs | 200 `PlanningView` после серверного расчёта и сохранения |

`PlanningView`: обязательные `version: integer >=0`, `editable: boolean`, `plotCheck: PlotCheck|null`, `calculation: Calculation|null`, `plotCheckCurrent: boolean`, `calculationCurrent: boolean`. До первой записи: version=0, оба результата=null, оба признака=false. `editable` учитывает наличие черновика, закрытие подготовки и завершение проекта, независимо от выбранного источника средств.

`PlotCheck`: обязательные `id`, `cadastralNumber`, `status`, `address`, `region`, `landCategory`, `permittedUse`, `reason`, `rate`, `termsVersion`, `checkedAt`, `isDemo:true`; типы и nullable из таблицы хранения. Для NOT_FOUND возвращать 200 со статусом, чтобы не путать его с недоступной карточкой. `plotCheckCurrent` означает совпадение нормализованного номера заявки и сохранённого результата; при пустом текущем номере false. Произвольная давность сама по себе не меняет этот признак, время проверки всегда видно.

`Calculation`: обязательные `id`, `plotCheckId`, `cost`, `depositPercent`, `depositAmount`, `years`, `joint`, `principal`, `rate`, `creditLimit`, `monthlyPayment`, `withinLimit`, `termsVersion`, `calculatedAt`, `isDemo:true`; все значения non-null. Денежные поля — JSON number с максимум двумя десятичными знаками, даты/время — ISO 8601 с часовым поясом, ID — UUID. `calculationCurrent=true` только при актуальной ELIGIBLE-проверке, совпадении её ID с plotCheckId и текущей версии условий. Исторические результаты сохраняются в ответе даже при false.

Версия условий в примерах PR фиксирована и не заменяется молча. Backend проверяет, что сохранённая ставка соответствует условиям сценария; при новой версии условий требует повторить проверку до нового расчёта.

| HTTP / code | Условие |
|---|---|
| 400 `VALIDATION_ERROR` | Недопустимый UUID/JSON/поле; пустой или неверный номер для проверки; недопустимые параметры расчёта |
| 401 `AUTH_REQUIRED` | Нет действующей сессии |
| 403 `INVALID_CSRF_TOKEN` | Изменяющий запрос без допустимого CSRF |
| 404 `PROJECT_NOT_FOUND` | Карточки нет или текущий пользователь не её владелец, включая подрядчика |
| 409 `STALE_REQUEST_VERSION` | Заявка изменилась после получения формы |
| 409 `REQUEST_LOCKED` | Нет редактируемого черновика, подготовка закрыта или проект завершён |
| 409 `STALE_FINANCING_PLAN` (новый) | Устарела версия планирования, проверка/условия или plotCheckId не относится к последней подходящей проверке этой карточки |
| 409 `IDEMPOTENCY_CONFLICT` | Ключ уже использован с другим нормализованным содержимым или другой операцией |
| 503 `BANK_DEMO_UNAVAILABLE` | Таймаут, недоступность или неверная схема ответа локального источника |

Ошибки имеют текущую схему `Problem`: `type:"about:blank"`, `title`, `status`, `code`; ошибки полей используют существующий `fieldErrors: object<string,string>`. Новые коды предварительно добавить в enum OpenAPI. Проверку прав выполнять до раскрытия состояния/ошибок предметной области. CSRF может отклонить запрос раньше контроллера штатным фильтром.

Пример тела сохранения расчёта (UUID показаны синтетическими):

```json
{
  "requestVersion": 2,
  "planningVersion": 1,
  "idempotencyKey": "11111111-1111-4111-8111-111111111111",
  "plotCheckId": "22222222-2222-4222-8222-222222222222",
  "cost": 5000000,
  "depositPercent": 20,
  "years": 20,
  "joint": false
}
```

Сервер возвращает расчёт с `principal:4000000`, `depositAmount:1000000`, `rate:3`, `creditLimit:6000000`, `monthlyPayment:22183.90`, `withinLimit:true`, `isDemo:true` и увеличенной версией планирования. Ставка и рассчитанные значения не принимаются в теле запроса.

### 5. Формула и демонстрационные условия

Стоимость C, взнос d%, срок Y, годовая ставка a%. Взнос D=C*d/100; кредит P=C-D; число платежей n=12Y; месячная ставка r=a/1200. Платёж A=P*r/(1-(1+r)^(-n)); при r=0 — P/n. Суммы на сервере рассчитывать с контролируемой десятичной точностью; финальный платёж округлять HALF_UP до копеек. По результатам отдельного UX-прохода предварительный и сохранённый платёж показываются одинаково до копеек, чтобы округлённое значение не выглядело изменением расчёта. Единый серверный расчёт — основание сохранения, браузерный просмотр сверяется с ним на примерах и границах округления.

Параметры диапазонов, ставок 3%/0,1%, лимитов 6/12 млн ₽ взяты из PR как синтетический набор `pr1-demo-v1`; они не утверждают действующие правила банка. Верхний лимит проверяется по P, не C. Ровно лимит допустим. Превышение не является технической ошибкой: сохраняется расчёт с withinLimit=false. Программа альтернативной ипотеки и её ставка из отрицательного экрана PR не переносятся без отдельного согласования.

### 6. Повтор, конкуренция и транзакции

1. Проверить сессию и владельца. Для уже успешно выполненного ключа сравнить нормализованное содержимое; вернуть сохранённый ответ даже если ожидаемые версии уже устарели. Актуальные права проверяются и при повторе. GET после повтора показывает текущее состояние, если оно изменилось позднее.
2. Под блокировкой проекта через публичную границу проверить черновик, requestVersion и planningVersion; получить снимок номера. HTTP-проверку через локальный источник выполнять вне транзакции, без удержания блокировки. Расширить существующий loopback Mock API маршрутом `/plot-check`; не создавать второй сервер или браузерный доступ к нему. Только синтетические данные, без адресов настоящих сервисов и банковских секретов.
3. После HTTP повторно проверить владельца, версии, состояние и номер под той же блокировкой проекта. В одной транзакции создать неизменяемый результат, обновить указатель и версию плана и записать результат команды. Внешняя ошибка или конфликт не меняет последнее сохранённое состояние.
4. Расчёт выполняется локально на backend и фиксируется одной короткой транзакцией с теми же проверками и блокировкой. Все команды планирования сериализуются общей блокировкой проекта; при одинаковых версиях две разные команды не перезаписывают друг друга.
5. Два одновременных одинаковых ключа могут выполнить два безопасных чтения Mock API, но после повторной проверки ключа и UNIQUE фиксируется одна запись и обе команды получают один результат. Другой payload с тем же ключом получает конфликт. При техническом сбое ключ не считается успешно выполненным и допускает повтор.

Новая проверка всегда получает новый ID и делает прежний расчёт историческим. Смена кадастрового номера штатным PATCH не требует записи в banking: актуальность вычисляется по текущей заявке при чтении/записи. Изменение других пожеланий после завершённой проверки само по себе не инвалидирует её; requestVersion защищает именно выполняющуюся команду от гонки. Созданная копия заявки имеет другой projectId и пустое планирование.

## Risks / Trade-offs

- Демоответ выглядит как реальная проверка → маркировать источник на результате и возле ставки, не переносить маркетинговые обещания PR.
- Сохранённый расчёт воспринимается как одобрение → отдельные подписи и данные, отсутствие автоматического изменения снимка и строительной заявки.
- Несохранённый номер расходится с проверяемым → явное сохранение перед запуском и повторная проверка версии после HTTP.
- Условия и объём не утверждены → текущая итерация остаётся предложением; сначала согласовать объём, затем обновить OpenAPI и реализовывать.
- Скриншоты прототипа скрывают отсутствие интеграции → снимать только интегрированное приложение, проверять кадры вместе с README при приёмке.

## Migration Plan

После согласования сначала расширить OpenAPI и тестовые схемы, затем добавить новую миграцию и backend, после — UI в текущем frontend и документацию. Миграция только добавляет таблицы; старые записи и миграции сохраняются. Откат приложения к прежней версии оставляет новые таблицы без использования, без удаления данных. Из PR переносить нужные элементы выборочно, не сливать отдельный продукт как условие интеграции. В реализации добавлена миграция V12, обновлены текущие backend, frontend и OpenAPI.

Этот change независим от будущих `demo-rural-mortgage` (обязательства), `track-construction-budget` (расходы) и `integrate-svoe-selo` (экосистемные события). Он использует уже внедрённую ипотечную демоинтеграцию, не реализует эти будущие changes и не архивирует их.

## Open Questions

- Расширять ли первую поставку демозаявкой и листом ожидания из PR? Текущий предлагаемый объём их исключает; включение требует отдельного уточнения сценариев, полей, статусов и безопасных повторов до реализации. Пользователь поручил реализацию предложенной первой итерации без расширения; демозаявка и лист ожидания оставлены за её рамками.
- Визуальный референс «Участок и ипотека»: в PR его скриншота нет. Перед UI-реализацией можно снять исходный прототип для сравнения композиции; обязательные финальные снимки всё равно снимаются с интегрированного приложения.
