# house-projects Specification

## Purpose
Объединяет заказчика и назначенного подрядчика вокруг карточки дома и изолирует её от остальных пользователей.

## Requirements

### Requirement: Создание карточки дома

Система SHALL создавать карточку с названием и местоположением участка для вошедшего заказчика. Владельцем становится текущий заказчик. Изначально подрядчик отсутствует. Для новой карточки создаётся черновик заявки, а исполняемые этапы отсутствуют до согласования предложения. Поле address хранит адрес или текстовое описание местоположения участка; кадастровый номер хранится отдельно в заявке. Название и местоположение могут совпадать у разных карточек. Ограничения полей заданы в `api/openapi.yaml`.

#### Scenario: Заказчик создаёт карточку
- **WHEN** вошедший заказчик отправляет допустимое название и местоположение
- **THEN** API возвращает 201, ссылку в заголовке Location и карточку с `contractorId: null`, а карточка появляется в его списке
- **AND** владелец может заполнить черновик заявки, начало работ недоступно

#### Scenario: Подрядчик пробует создать карточку
- **WHEN** вошедший подрядчик отправляет запрос создания
- **THEN** API возвращает 403 `FORBIDDEN` и не создаёт карточку

#### Scenario: Пустые поля
- **WHEN** заказчик передаёт название или местоположение только из пробельных символов
- **THEN** API возвращает 400 `VALIDATION_ERROR` и не создаёт карточку

### Requirement: Назначение подрядчика

Система SHALL разрешать владельцу карточки назначить одну организацию подрядчика через нормализованный email её руководителя. Перед подтверждением показываются название организации, ИНН и основной контакт. Для новых назначений обязательны заполненные имя и профиль организации. Поле contractorId сохраняет ID основного контакта для совместимости, contractorOrganizationId хранит организацию; членство и команда конкретной стройки определяют доступ сотрудников. Email обычного сотрудника не назначает новую организацию неявно: возвращается ошибка адресата с предложением указать основной контакт. Назначение доступно через карточку владельца. Повтор того же назначения возвращает текущее состояние, а попытка назначить другого подрядчика после первого назначения отклоняется. В новом процессе подрядчик получает доступ после отправки заявки; для проектов прежнего процесса доступ открывается при назначении.

#### Scenario: Назначение и повтор
- **WHEN** владелец указывает email зарегистрированного подрядчика и повторяет тот же запрос
- **THEN** каждый запрос возвращает 200 с одними и теми же `contractorId` и `contractorOrganizationId`
- **AND** в новом процессе подрядчик увидит карточку после отправки заявки, а в прежнем — сразу

#### Scenario: Неподходящий аккаунт
- **WHEN** владелец вводит email без подходящего аккаунта подрядчика, включая email заказчика
- **THEN** API возвращает 422 `CONTRACTOR_NOT_FOUND`, назначение не меняется

#### Scenario: Назначение другого подрядчика
- **WHEN** владелец указывает другого зарегистрированного подрядчика после назначения
- **THEN** API возвращает 409 `CONTRACTOR_ALREADY_ASSIGNED`, исходное назначение сохраняется

#### Scenario: Одновременное назначение
- **WHEN** владелец одновременно назначает двух разных подрядчиков в одну свободную карточку
- **THEN** одно назначение возвращает 200, второе — 409, назначается один подрядчик

#### Scenario: Назначение участником без права записи
- **WHEN** назначенный подрядчик отправляет запрос назначения для доступной ему карточки
- **THEN** API возвращает 403 `FORBIDDEN`, назначение сохраняется

#### Scenario: Команда организации
- **WHEN** заявка отправлена, руководитель организации добавляет юриста в команду только этой стройки
- **THEN** юрист видит её согласно выданному доступу, другие стройки организации не раскрываются

#### Scenario: Старый одиночный подрядчик
- **WHEN** открывается карточка без привязанной организации
- **THEN** прежний назначенный аккаунт сохраняет доступ, реквизиты не выдумываются, новые сотрудники не получают доступ автоматически

#### Scenario: Подключение профиля к прежним карточкам
- **WHEN** прежний назначенный подрядчик создаёт собственную организацию и выбирает «Подключить команду» в своей карточке
- **THEN** карточка привязывается к его организации с тем же основным контактом, а текст договора и исторические подписи сохраняются; чужую карточку или чужую организацию подключить нельзя

### Requirement: Изоляция карточек

Система SHALL выдавать заказчику только собственные карточки, а подрядчику только назначенные ему карточки с отправленной заявкой. Назначение не открывает подрядчику черновик заявки. Список возвращается от новых к старым с устойчивой сортировкой по ID при равном времени. У аккаунта без карточек список пуст. Для ранее созданных проектов, обозначенных как прежний процесс, сохраняется существующий доступ к карточке и этапам.

#### Scenario: Запрос чужой карточки
- **WHEN** вошедший пользователь вне карточки запрашивает её по ID или пытается изменить назначение
- **THEN** API возвращает 404 `PROJECT_NOT_FOUND`, совпадающий с ответом для отсутствующего ID
- **AND** чужая карточка отсутствует в списке пользователя

#### Scenario: Назначен до отправки
- **WHEN** подрядчик назначен на новую карточку, но заказчик ещё не отправил заявку
- **THEN** карточка отсутствует в списке подрядчика и недоступна ему по ID

#### Scenario: Запрос карточек без входа
- **WHEN** браузер без действующей сессии запрашивает список или карточку
- **THEN** API возвращает 401 `AUTH_REQUIRED`

### Requirement: Участники видят паспорт дома с происхождением значений

Система SHALL показывать заказчику и участникам назначенной команды read-only паспорт внутри существующей карточки: площадь, этажность, материал стен, тип фундамента, кровлю и срок. Источники SHALL различаться: площадь и этажность — текущая доступная строительная заявка, технические характеристики — отдельно заполненные общие сведения дома, плановый срок — максимальная плановая дата завершения исполняемого согласованного плана. Для LEGACY срок берётся из его действующего плана. До появления такого плана желаемая дата окончания из заявки SHALL отображаться только как «Желаемое завершение», а не согласованный срок.

Значения SHALL NOT восстанавливаться по названию проекта, свободному тексту пожеланий, умножению габаритов вместо сохранённой площади или по фотографии. Отсутствующие значения SHALL передаваться как null и отображаться как «Не указано»; при отсутствии всех значений показывается компактное пояснение без пустой большой панели. Наличие части полей SHALL NOT скрывать остальные заполненные поля. При завершении дома паспорт сохраняет чтение и подпись об источниках, не становится подтверждением фактических характеристик.

Площадь и этажность SHALL NOT дублироваться во второй изменяемой записи паспорта. В первой итерации пользовательского редактора дополнительных технических характеристик нет; они могут отсутствовать у обычных проектов. Демонстрационный набор заполняется контролируемой командой разработки. Будущее редактирование требует отдельного контракта и не меняет отправленную заявку задним числом.

#### Scenario: Все сведения доступны
- **WHEN** участник открывает проект с заявкой, заполненными техническими сведениями и согласованным планом
- **THEN** он видит все шесть характеристик, дату планового завершения из плана и пояснение источников

#### Scenario: Старый объект без паспорта
- **WHEN** участник открывает LEGACY-проект без заявки и технических характеристик
- **THEN** карточка открывается без ошибки, фиктивные параметры не появляются; имеющаяся дата плана доступна независимо от остальных полей

#### Scenario: Частично заполненная заявка
- **WHEN** площадь и этажность заданы, а фундамент и кровля неизвестны
- **THEN** известные значения видны, неизвестные обозначены текстом; никаких демонстрационных значений для обычного проекта нет

#### Scenario: Изменение источника
- **WHEN** заказчик сохранил допустимое изменение площади черновика либо изменился разрешённый план LEGACY
- **THEN** следующее чтение паспорта показывает соответствующее сохранённое значение, а второй независимой копии для синхронизации не существует

#### Scenario: Желаемый срок до согласования плана
- **WHEN** у заявки есть желаемая дата завершения, но исполняемого плана нет
- **THEN** видна подпись «Желаемое завершение» и источник «Пожелания заказчика»

#### Scenario: Неполный план не даёт обещанного срока
- **WHEN** план существует, но хотя бы у одного этапа отсутствует плановая дата окончания
- **THEN** паспорт не выдаёт максимум остальных дат за срок всего дома; плановый срок равен null, пожелание при наличии остаётся отдельно обозначенным

#### Scenario: Чужой пользователь и закрытые данные
- **WHEN** посторонний аккаунт обращается к паспорту по прямому API URL
- **THEN** получает 404 PROJECT_NOT_FOUND; ответ для разрешённого подрядчика не содержит бюджета, кадастровой проверки и ипотечного расчёта

#### Scenario: Обновление существующей базы
- **WHEN** приложение обновляется на базе с уже применённой миграцией V12 участка и ипотеки
- **THEN** новые структуры паспорта добавляются без конфликта версий и изменения прежних строк, заявки, расчёты, файлы и доступ к ним сохраняются
